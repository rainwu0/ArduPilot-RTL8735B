# 上板驗證紀錄

README〈功能狀態〉標「板上驗證」的項目，都在這裡有一筆紀錄。每筆綁定建置時的提交，只增不改；結果被推翻時加一筆新的，舊的留著並註明被哪一筆取代。主機測試與只建置的結果不寫在這裡。

原始 log 不在儲存庫裡，紀錄只摘錄關鍵的幾行。

### T1 沒有感測器的開機與 Wi-Fi 連線

- 日期：2026-10-13
- 提交：`ebcbb5a8f6`
- 建置：`./waf configure --board hub8735ultra`、`./waf copter`；`RTL8735B_WIFI_CONFIG` 指向本機的 Wi-Fi 設定檔（見〈Wi-Fi〉）；`FLASH_LAYOUT` 預設；SDK `d1b6426`、Realtek ASDK 10.3.0
- 映像：`flash_ntz.bin` sha256 `86b4c8721db799a9a01be1f59075b59cdee7c6d0d39199781889f685343a8b1d`（含 Wi-Fi 帳密，別人建不出同一個值）；Flash 版面 `realtek-ota`；Wi-Fi UDP，本機埠 14555
- 開發板：HUB 8735 ultra
- 接線與感測器：沒有接任何感測器；USB 供電；沒有接馬達與電調
- 步驟：
  1. 以序列埠手動燒錄（見〈手動燒錄〉）。
  2. 錄 LOG UART，按 reset。
- 預期：開機、連上 Wi-Fi；沒有氣壓計，所以停在氣壓計的 Config Error。
- 結果：通過（只限上面兩項）。關鍵輸出：

- 怎麼確認對象是這塊開發板：只用這塊開發板的序列埠，沒有做網路檢查。
- 沒測到的：Wi-Fi MAVLink、參數保存、TCP、`--upload`，以及所有感測器。

### T2 範例疊加檔：感測器、Wi-Fi MAVLink（UDP）、參數保存、姿態

- 日期：2026-10-14
- 提交：`0320831602`
- 建置：`./waf configure --board hub8735ultra --extra-hwdef <本機疊加檔>`、`./waf copter`。本機疊加檔第一行 `include` 範例疊加檔 `hwdef/hub8735ultra/sensors-example.dat`，另外把 `HAL_RTL8735B_WIFI_UDP_LOCAL_PORT` 改成 14557、`MAV_SYSTEM_ID` 定成 3，沿用受測板原本的設定，和感測器無關。`RTL8735B_WIFI_CONFIG` 指向本機的 Wi-Fi 設定檔；`FLASH_LAYOUT` 預設；SDK `d1b6426`、Realtek ASDK 10.3.0
- 映像：`flash_ntz.bin` sha256 `cff481f131dbdb113cdd4cc84898cec36d75427d34d430e1577ce38d687d3cbe`（含 Wi-Fi 帳密，別人建不出同一個值）；Flash 版面 `realtek-ota`；Wi-Fi UDP，本機埠 14557、地面站埠 14550
- 開發板：HUB 8735 ultra
- 接線與感測器：照〈接上感測器〉，GY-BMI160（SPI）、BMP280、GY-271（QMC5883L），都焊在板上；BMI160 元件面朝上，前方是 USB 接頭的另一端。USB 供電；沒有接馬達、電調與電池
- 步驟：
  1. 以序列埠手動燒錄，錄 LOG UART 的開機訊息。
  2. 地面站工具在電腦上收 UDP 14550，只接受這塊開發板 IP 的封包：先收心跳 10 秒，再下載全部參數。同一段時間繼續錄 LOG UART。
  3. 把 `PILOT_SPD_UP` 從 2.5 寫成 3，等 10 秒，送重開機指令，重開後讀回，最後寫回 2.5。同一段時間錄下重開機的完整開機訊息。
  4. 請飛控以 10 Hz 送 `ATTITUDE`，錄 45 秒：先水平靜止，再把前方抬起約 45°、放平，再把後方抬起約 45°、放平。
- 預期：開機沒有 `Config Error`；三個感測器都被偵測到（`INS_ACC_ID`、`BARO1_DEVID`、`COMPASS_DEV_ID` 都不是 0）；參數在重開機後保留；水平時 roll、pitch 接近 0，前方抬起時 pitch 為正、後方抬起時為負。
- 結果：通過。關鍵輸出：
  - 開機（步驟 3 的重開機，完整錄到）：`Config Error` 出現 0 次。
    ```
    WiFi: up, local 192.168.137.49:14557
    WiFi: ground station 192.168.137.1:14550
    QMC5883L found on bus 1 id 855305 address 0x0d
    ```
  - 心跳：10 秒 10 則，系統編號 3，未解鎖。參數：927 筆全部收到，`INS_ACC_ID` 589834、`BARO1_DEVID` 226825、`COMPASS_DEV_ID` 855305。
  - 參數保存：寫入 3，重開機後讀回 3，最後寫回 2.5。
  - 姿態：

    | 時段 | roll | pitch |
    |---|---|---|
    | 水平靜止 | 1.4° | 0.3° |
    | 前方抬起 | 約 5° | 41° |
    | 後方抬起 | 約 7° | −46° |
    | 放回水平 | 1.4° | 0.2° |

- 怎麼確認對象是這塊開發板：
  1. 檢查工具只接受 192.168.137.49 的封包，這個 IP 取自同一塊開發板序列埠印出的 `WiFi: up, local 192.168.137.49:14557`；
  2. 步驟 2 期間，同一塊開發板的序列埠印出 `WiFi: ground station 192.168.137.1:14550`（電腦的 IP）；
  3. 心跳的系統編號是 3，是這塊開發板專用的值。
- 同一天的其他結果（照實記錄）：
  - 前一版的範例疊加檔（IMU 寫 `ROTATION_NONE`）在同一塊板上：開機、心跳、參數、參數保存都通過，但水平放著時 roll 讀到約 180°，表示上下顛倒。依實測改成 `ROTATION_ROLL_180_YAW_270`，就是上面的提交。
  - 提交 `0320831602` 的映像燒錄後，第一次開機出現 `Config Error: Baro: unable to initialise driver`。之後按 reset 一次、以 MAVLink 重開機一次，氣壓計都正常。接線是焊死的。原因未明；和〈功能狀態〉I²C 列記的「開機時氣壓計偶發初始化失敗」是同樣的現象，這是推論，沒有查證。
- 沒測到的：
  - roll 的正負：只測了前方、後方抬起；roll 的方向由元件面朝上與 pitch 的結果推得，屬於推論；
  - 羅盤的方向與校正（只確認有被偵測到）、加速度計校正、yaw；
  - 斷電後參數是否保留（只測了重開機）；

### T3 I²C 開機清匯流排：不斷電重開機時氣壓計的初始化

- 日期：2026-10-16、2026-10-17
- 提交：映像不是由本儲存庫的提交建置，而是由未公開的專案以同一份 HAL 修改加上未公開的應用程式建置。I²C 的程式（`bus_shim.c`、`I2CDevice.cpp`）和本儲存庫的 `7c010012fd` 相同，只差三行註解的用字；沒有之後的 `bffd9a9748`、`bd1ea0f7a2`（每條匯流排各自的狀態與 task）。
- 映像：依建置與燒錄時的紀錄；開發板上沒有以版本雜湊確認。兩天各一份，I²C 的程式相同。
- 開發板：HUB 8735 ultra，和 T2 同一塊（Wi-Fi IP 192.168.137.49、系統編號 3）
- 接線與感測器：和 T2 相同，BMP280 與 QMC5883L 在 I²C 匯流排 1、BMI160 在 SPI，都焊在板上。只接 USB；沒有接電池、馬達與電調。不解鎖。
- 步驟：
  1. 10/16：寫入映像後的第一次開機，再以 MAVLink 熱重開 3 次（不寫參數），錄 LOG UART 的開機訊息，看氣壓計是否健康。
  2. 10/17：以 MAVLink 熱重開 16 次，每次等心跳恢復；另外 4 次熱重開來自同一段時間寫電池參數後的重開機（不寫 I²C 相關的參數）。最後由維護者拔插 USB 冷開機一次，下載全部參數。
- 預期：每次開機都沒有 `Config Error: Baro`；冷開機後三個感測器都被偵測到。
- 結果：通過。
  - 10/16：4 次開機，氣壓計都健康，`STAT_BOOTCNT` 19 → 23（第一次開機後 20，三次熱重開後 23）。第 3 次熱重開的開機開頭沒錄到（序列埠重新開啟時已到連 Wi-Fi 的階段），錄到的部分沒有 `Config Error`；`Config Error` 每 5 秒重印，所以推論那次也沒有。
  - 10/17：16 次熱重開在 7.7–13.1 秒內恢復 Wi-Fi 的心跳（系統編號 3）；另外 4 次也恢復了心跳並讀回參數，恢復時間沒有記錄。停在 `Config Error` 時不會有 Wi-Fi MAVLink（見 T1），所以這 20 次都沒有停在 `Config Error`。
  - 冷開機：開機後第一次下載的參數 `INS_ACC_ID`、`COMPASS_PRIO1_ID` 是 0；接著做 20 秒的心跳檢查，收到 20 則心跳，未解鎖；之後再下載（和第一次下載完成相隔約 55 秒），就和開始前相同（`INS_ACC_ID` 589834、`BARO1_DEVID` 226825）。推論是第一次下載時慣性感測器與羅盤還在初始化；之後下載仍是 0 就推翻這個推論。
- 怎麼確認對象是這塊開發板：檢查工具只接受 192.168.137.49 的封包，心跳的系統編號是 3，和 T2 相同。
- 和 T2 的關係：T2 記的「燒錄後第一次開機出現 `Config Error: Baro`」在這 25 次開機（熱重開 23 次、寫入映像後的第一次開機與冷開機各 1 次）中都沒有出現。原因推論是重置時 I²C 裝置拉住 SDA（見 `7c010012fd` 的提交訊息）；這裡的結果和推論一致，但沒有直接看到 SDA 被拉住。
- 沒測到的：
  - 按 reset 鍵的重置（沒有做）與看門狗重置；
  - 傳輸逾時後的重新初始化、清匯流排與停用；
  - 多條 I²C 匯流排，以及 `bffd9a9748`、`bd1ea0f7a2` 之後的程式。

### T4 主迴圈：正常運作的頻率、IMU 斷線時其他 task 是否照常

- 日期：2026-10-16（甲）、2026-10-17（乙）
- 提交：映像不是由本儲存庫的提交建置，而是由未公開的專案以同一份 HAL 修改加上未公開的應用程式建置。兩份映像的 `Scheduler.h` 和本儲存庫的 `6ea8e665d0` 相同，`Scheduler.cpp` 只多了重開機前呼叫應用程式的兩行與註解，和讓出無關。
- 映像：依建置與燒錄時的紀錄；開發板上沒有以版本雜湊確認。
- 甲：正常運作時的主迴圈
  - 開發板：HUB 8735 ultra，和 T2、T3 同一塊（192.168.137.49、系統編號 3），感測器同 T3；只接 USB，不解鎖。
  - 步驟：把 `SCHED_DEBUG` 暫時設成 1，從 Wi-Fi MAVLink 收 120 秒的 `PERF` 訊息（每 10 秒一則）；結束時把 `SCHED_DEBUG` 寫回 0。電腦端的主迴圈頻率是相鄰兩則 `PERF` 之間的圈數除以電腦收到兩則的時間差，漏收或延遲到達的那段不算。
  - 結果：電腦端算得 399.9 Hz（設定 400 Hz）；12 段 10 秒的 `PERF` 都是 `F=400Hz`；長迴圈 0.07%（48,000 圈中 32 圈，每段 2–4 圈）；最長單圈 4.65 ms。
  - 這一項只說明加了讓出之後，正常運作的主迴圈仍是 400 Hz；最長單圈遠低於 20 ms，表示這段時間沒有出現讓出要處理的連續忙等。
- 乙：拔 IMU 的 SCLK
  - 開發板：HUB 8735 ultra，另一塊（Wi-Fi IP 192.168.137.35）；BMI160 以杜邦線接在 SPI，沒有其他感測器；只接 USB，不解鎖。
  - 步驟：維護者在場拔掉 BMI160 的 SCLK，約 3 分鐘後接回，再拔插 USB 重開機。全程由未公開的應用程式每 2 秒經 UDP 回報主迴圈的間隔，並從電腦每 5 秒連一次應用程式的另一個網路服務，看它有沒有回應。
  - 結果：拔掉 SCLK 後加速度與角速度停在 0，PreArm 檢查回報 `EKF attitude is bad`；這段時間主迴圈的間隔 2–3 ms、最長 3 ms，網路服務每 5 秒都有回應。接回並重開機後，加速度大小 997.3 mG，健康檢查正常。
  - 同一段時間先拔了另一條 IMU 線，IMU 照常有讀數，不算數。
- 怎麼確認對象是這塊開發板：甲同 T3；乙只看 192.168.137.35 送來的封包。
- 判讀：乙的主迴圈沒有卡住，加速度與角速度是 0 而不是停在最後的值，推論是 SCLK 拔掉後 IMU 的驅動程式照樣讀到樣本（全是 0），`wait_for_sample()` 沒有空轉，所以讓出可能沒有觸發。乙證明的是「拔掉 IMU 的 SCLK 時主迴圈與較低優先權的 task 照常」，不能證明讓出在 IMU 完全不送樣本時有效。能推翻這個推論的：加計數的映像在同樣操作下記到讓出。
- 沒測到的：IMU 完全不送樣本（例如拔掉片選或電源）時的主迴圈與其他 task；讓出實際觸發的次數；負載較重時讓出造成的延遲。
